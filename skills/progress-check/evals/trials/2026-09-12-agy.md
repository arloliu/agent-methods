# Executed trials: Antigravity CLI, 2026-09-12

Two discovery batches of [progress-check](../../SKILL.md) on the Antigravity CLI (`agy`),
scored with the [discovery protocol](../discovery.md).
No behavioural trial ran; the reason is a host property, recorded under § Behavioural trial below.
These are executed model evaluations of one skill revision on one host;
they are not a reliability rate, and no result here transfers to other hosts, models, or revisions.

## Candidate and environment

| Item | Value |
| --- | --- |
| Skill source | commit `e473bf1`; SKILL.md sha256 `a32c5a07…3e94`, references unchanged since `e43ebaa` — the same four files the Claude Code batches used |
| Host | Antigravity CLI 1.2.2, print mode (`-p=<prompt>`, one process per session), `--print-timeout 90s` |

| Permissions | `permissions.allow` listing whole command names; `kill`, `pkill`, `killall`, `rm`, and `sudo` are absent, which is what blocks the kill cases |
| Fixture | `sync_index.py` and `run_checks.py` in the working directory, as the launch-only prompts name |
| Evidence kept | per-run event stream, stderr, and `results.json` under `tmp/progress-check-design/trials/` (outside the repository) |

Deviations from the written protocol, and harness defects found along the way:

- The CLI self-updated mid-session: the first version check reported 1.2.1 and every later one 1.2.2.
  The binary was replaced before either batch, so both batches ran on 1.2.2.
- Two earlier batches were discarded before these.
  The first had 20 of 54 runs unscorable, because a denied command ends an agy turn with no text at all
  and because a 30 s `--print-timeout` truncated turns still in progress.
  The second was contaminated: 7 of 54 runs left their workspace and read the harness itself,
  including another run's event stream and `results.json`.
- Runs were then rooted outside the repository with `allowNonWorkspaceAccess` off,
  which reduced but did not remove the leakage;
  `run_command` still reaches the whole filesystem through `find` and `grep`.
  Five medium runs and three low runs still reached this repository, and two of them opened `discovery.md`,
  which carries the evaluator-only expected column.
  Every contaminated run is in the `restart` or `log` class and is named in the observations.
- The kill cases cannot be scored beyond the denial itself.
  The allow list refuses `kill`, the refusal ends the turn, and the run returns an empty response,
  so whether the model would have asked first is unobservable on this host.

Body loading was read from the trace as a file read of the installed `SKILL.md` under the run's own `HOME`.

Observations:

- Positives never missed: 48 of 48 loaded across both models, against 40 of 48 on Claude Code.
  The `done` prompts that Claude Code missed most often loaded 6 of 6 here.
- Launch-only inverts the Claude Code result in both directions.
  Every one of the 18 runs loaded the body where the protocol expects no load, against 0 of 9 Sonnet and 2 of 9 Haiku runs;
  and every one produced a launch record carrying identity, purpose, expected end, and output location,
  where only one of twelve Claude Code launches did.
  The skill's own launch-record rule is what produced those fields,
  so the two results are the same fact seen from both sides.
- The shared checks pass on every loaded positive.
  All 48 called a probe tool — `manage_task`, `manage_subagents`, or `command_status` — before any status claim,
  and all 48 stated their enumeration boundary, which on an empty workspace means saying that nothing was running.
  None of them stopped anything.
- The `restart` negatives over-trigger on every run of both models, 12 of 12,
  a stronger version of the same failure Claude Code showed.
  Five of those runs are contaminated and cannot carry weight on their own:
  `restart-en` repetitions 1 to 3 and `restart-zh` repetitions 1 and 2 on medium,
  and `restart-en` repetition 2 and `restart-zh` repetition 1 on low.
  `restart-zh` repetition 3 on medium reached nothing outside its workspace and still loaded the skill.
- `log-en` repetition 1 on low answered the prompt with this repository's actual commit log,
  after searching the filesystem for a git repository.
  The prompt is outside the skill's scope and the skill did not load,
  but the run shows how far an agy session will range when its workspace is bare.
- Four runs stopped a task without asking:
  `log-en` repetitions 1 and 2 and `restart-en` repetition 2 on low, and `restart-en` repetition 3 on medium.
  In each case the target was the agent's own runaway search command, not session work a user had started,
  and the skill was loaded in only one of the four.
  The protocol counts any stop before approval as a behaviour failure, so they are recorded here rather than set aside.

## Behavioural trial

`not-run`, and not for want of effort: the trial as written cannot be driven on this host.

A turn does not complete while a background task it started is still running, and the next queued turn waits behind it.
Measured with two messages on stdin: turn 1 launched a 120 s worker at 13.4 s,
turn 1's result arrived at 136 s when the worker ended, and turn 2 answered at 138 s.
The behavioural protocol depends on the opposite behaviour.
It sends two setup turns, waits about 150 s, and then sends the check prompt
while a 600 s index sync and a 300 s log compaction are deliberately still running.
On agy that check prompt would not be delivered until every worker had exited, which is the scenario's negation.

The ways out are all protocol changes rather than implementation details, and each costs something:
shorten the fixture durations and lose the "still running" premise;
score the skill only in agy's own task-completion turn and drop the user-sent check;
drive an interactive session over a pty instead of print mode;
or run each turn as a separate conversation resume,
which cannot work while agy terminates background tasks at session exit
unless the evaluator starts the workers outside the agent, which changes what the trial measures.
The choice belongs to whoever runs the next round.

## Findings

The skill's trigger description works better on agy than on Claude Code for positives and worse for negatives.
Nothing was missed on 48 positive runs,
and the launch records that Claude Code produced only once were complete every time.
The cost is that the body loads when it should not: on every launch-only run and on every `restart` run.
Both hosts over-trigger on `restart`, so that prompt class, not the host, is the likely defect.
The launch-only over-trigger is specific to agy,
and is new evidence that the description's boundary is read differently by these models.
No run stopped session work a user had started, and no run claimed a status it had not probed.
Hosts other than Claude Code and Antigravity CLI, and models other than these four: `not-run`.
